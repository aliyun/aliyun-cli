# CLI 制品怎么「信得过」：问题根源与建议方案

> 状态：设计提案（通俗版）  
> 适用：主 CLI 自升级、插件索引 `plugin_pkg_index`、插件包下载  
> 更细的机制说明见：[公私钥完整机制](../../二进制分发中的公私钥_发布侧与客户端侧完整机制.md)、[密钥轮转](../../私钥、公钥轮转.md)

---

## 先说结论（给赶时间的人）

我们现在的校验，本质上是在问一句话：

> 「下载下来的文件，和 **某份清单里写的哈希** 一不一样？」

这只能证明：**文件没传坏、也没人只换了包却忘了改清单**。  
它 **不能** 证明：「这份清单本身是不是官方写的」。

如果攻击者能改 CDN / OSS 上的内容，他可以 **同时改清单和哈希**，客户端照样「校验通过」。  
这就是审计里说的「供应链真实性缺口」——不是 checksum 没用，而是 **checksum 和包放在同一信任域里时，挡不住「整站被改」**。

**建议：**

1. **继续保留** 二进制的 checksum（有用）。  
2. **不要** 指望「再给 index.json 加一层 checksum、仍放在同一 CDN」来解决问题——信任边界没变。  
3. **要对「清单是不是官方发的」负责**，就要用 **公私钥签 index**（以及自升级清单）：私钥只在发布侧，公钥钉在 CLI 里。  
4. 落地分两步：先签 index + 堵住自升级裸奔；再做信任分层，方便换钥和泄露吊销。

## 一、从根源讲：我们到底在防什么？

装插件、升级 CLI，可以想成用户去「官方货架」拿东西。安全上其实要防三类事：

| 问题 | 白话 | 典型手段 |
|------|------|----------|
| **完整性** | 文件中途有没有坏、有没有被偷偷换掉一块？ | SHA-256 等 checksum |
| **真实性** | 这份说明 / 这个包，是不是 **我们官方** 发布的？ | 数字签名（公私钥） |
| **新鲜性** | 是不是有人故意塞给你一份 **很旧但曾经合法** 的清单？ | 版本号只增不减 + 过期时间 |

三件事不要混：

- **「对得上」≠「该信」**  
  checksum 回答「对得上」；签名回答「该信这份清单」。
- **HTTPS** 防的是「路上被人窃听/篡改」（在证书体系正常时）。  
  若攻击者已经能往 **你们自己的 CDN 写文件**，HTTPS 帮不上忙——他就是「合法站点」在发假货。
- **「普通哈希算法」不是签名**  
  SHA-256 谁都能算。攻击者改完文件，自己再算一个新哈希写上去即可。  
  真正能「只有官方能盖章、任何人能验章」的，是 **非对称签名**（私钥盖章、公钥验章）。

## 二、我们今天实际在做什么？

以插件为例，大致是：

```text
1. 客户端下载 plugin_pkg_index.json（里面有各平台包的 url + checksum）
2. 再按 url 下载二进制
3. 算一下二进制的哈希，和 index 里写的比一比
```

所以：**信任完全建立在「这份 index 是真的」之上。**  
index 真 → checksum 有用；index 假 → checksum 只会帮攻击者「自圆其说」。

另外两条短板更明显：

- **主 CLI 自升级**：很多路径是 CDN 直下，**连二进制 checksum 都没有**，比插件更弱。  
- **任意 URL / 本地包安装**：本来就不在官方货架上，不应假装和官方同源一样安全。

### 常见误解 1：「把 checksum 和二进制拆到两个 CDN 路径就安全了」

不行。若两边还是 **同一套账号 / 同一套发布权限** 能写，攻击者改两次就行。  
拆路径解决不了「信任锚在哪」的问题，只是多走几步。

### 常见误解 2：「再给 index.json 加一层 checksum，就不用公私钥、也不用轮转了」

听起来省事：以前只有二进制 checksum，现在多验一次 index 的哈希。

关键还是那句：**期望的 index 哈希从哪来？**

| 放哪 | 结果 |
|------|------|
| 和 index 放同一个 CDN（旁边一个 `.sha256`） | 攻击者一起改 → **和现在几乎一样** |
| 写死在 CLI 二进制里 | 每次改 index 都要发新 CLI，或只能钉死某一版——**比换公钥更难运营** |
| 从另一个「官方站」人工粘贴 | 只是换了一条通道；那条通道被控，问题照旧 |

所以：**多一层 index checksum，没有取消「私钥轮转」，往往是根本没获得真实性。**  
若团队明确接受「CDN/发布账号被控 ≈ 游戏结束」，可以继续只靠 checksum + HTTPS，但应在风险清单里写清楚：**不做真实性，而不是「加了 index checksum 就算签了」。**

### 常见误解 3：「一定要给每个 tar.gz 都签一份？」

不必。最优做法是 **签一份小清单（index）**，清单里再写每个包的 checksum。

```text
大文件（插件包）──哈希──► 写进 index（小）──私钥签名──► 签名（更小）
客户端：先验签名 → 再按 index 验大文件
```

这样发布侧（尤其是 KMS）只签几 KB，不用对每个平台包做一次密码学签名。

### 常见误解 4：「公私钥是不是『私钥加密、公钥解密』？」

分发场景里不是。正确心智是：

- **私钥** = 只有官方能用的「盖章笔」（放 KMS / 离线，绝不进 CDN）  
- **公钥** = 印在 CLI 里的「验章模板」（可以公开）  
- 算法建议：**Ed25519**（或 minisign 一类成熟方案）

没有「既能公开校验、又不靠非对称、又能防伪造」的捷径；HMAC 之类要把密钥塞进每个客户端，等于密钥公开。

## 三、建议方案：签清单 + 分层信任

### 3.1 核心原则（四句话）

1. **完整性**：继续用 checksum（放在清单里）。  
2. **真实性**：用私钥签 **整份 index / 升级清单**；CLI 用内置（或经 Root 授权的）公钥验签。  
3. **新鲜性**：清单带单调递增的 `index_version`，以及 `expires_at`；本地记住「见过的最大版本」，拒绝回滚和过期。  
4. **可运营**：客户端长期只钉 **Root 公钥**；日常签 index 的业务钥可以换、可以吊销——这才是「轮转」该解决的问题，而不是用「不加签名」来回避。

### 3.2 目标样子（概念）

```text
发布侧（portal / CI）
  ├─ 算出各平台包的 sha256，写入 plugin_pkg_index.json
  ├─ 填上 index_version、expires_at
  └─ 用 KMS 里的私钥对整份 index 签名 → 上传 index + .sig

客户端（aliyun-cli）
  ├─ 下载 index + 签名
  ├─ 用信任的公钥验签（失败则中止，默认不给跳过）
  ├─ 检查版本 / 是否过期
  └─ 再下载二进制，核对 checksum
```

自升级走 **同一套思路**（独立的升级清单也可以），避免「插件签了、升级路径还裸奔」。

### 3.3 东西分别存在哪？（KMS 不存 root.json）

先把两类东西分开：

| 东西 | 是什么 | 存哪 |
|------|--------|------|
| **私钥** | 盖章用的秘密 | **KMS / HSM / 离线 U 盘**（绝不上 CDN） |
| **root.json、index、签名文件** | **公开**元数据，谁都能下 | **和插件包同一套 CDN / OSS**（例如现有制品站） |

**KMS 只保管私钥（或提供「把摘要拿来、我帮你签一下」的 API）。**  
它不负责存 `root.json`。`root.json` 是一份普通的、可公开下载的 JSON：里面写「当前哪些公钥有权签插件 index / 升级清单」，再用 **Root 私钥**（往往比业务钥更敏感，甚至不上日常 KMS、而用离线仪式）盖章。

推荐的「三处落点」：

```text
1) CDN/OSS（在线货架，和 plugin_pkg_index 同域即可）
   /trust/root.json              ← 最新授权关系（公开）
   /trust/timestamp.json         ← 可选，短命新鲜度证明（公开）
   /plugins/plugin_pkg_index.json
   /plugins/plugin_pkg_index.json.sig

2) CLI 二进制内嵌（开机信任锚）
   - Root 公钥（或内嵌一份初始 root.json 快照）
   - 可选：minAcceptableRootVersion（拒绝过旧的 root）

3) 用户机器本地缓存（验过之后才写入）
   ~/.aliyun/trust/root.json     ← 客户端接受过的最高版本
```

客户端逻辑可以记成：

1. 启动时：以 **内嵌 Root 公钥 / 内嵌 root 快照** 为底线。  
2. 联网时：从 CDN 拉 `root.json`；用已信任的 Root 公钥验签；版本必须 **只增不减**；通过后写入本地缓存。  
3. 再用 root 里授权的业务公钥，去验 CDN 上的 `plugin_pkg_index` 签名。

所以：

- **攻击者改 CDN 上的 root.json** → 没有 Root 私钥就盖不出合法章 → 客户端拒绝。  
- **KMS 被用来签 index** → 只说明「业务私钥在云上受控使用」，**不**等于 root.json 存在 KMS 里。  
- **MVP 若还没上分层**：可以暂时没有独立的 `root.json`，只把业务公钥焊在 CLI 里；等要可换钥/可吊销时，再把「授权关系」外置成 CDN 上的 `root.json`。

### 3.4 为什么还要谈「密钥轮转」？

有人会说：一上公私钥就要轮转，好麻烦，还不如只加 checksum。

其实：

- **不加签名**：没有私钥可轮转，也 **没有** 抗「整站伪造」的能力。  
- **加了签名**：才出现「钥怎么换、泄露怎么办」——这是用一点运营成本，换真实的安全能力。

更重要的是：**真正麻烦的是「把业务公钥焊死在 CLI 里」**，不是「用公私钥」本身。

| 做法 | 计划内换钥 | 业务钥泄露 |
|------|------------|------------|
| 业务公钥焊死在每个 CLI 版本里 | 必须全员升 CLI | 两难：继续认泄露钥，或让老客户端全挂 |
| **分层：只钉 Root，业务钥由 Root 授权** | 发一份新的 `root.json` 即可 | 吊销旧钥、启用新钥，**多数用户不用升 CLI** |

「双签一段时间」只适合 **计划内换钥过渡**，**救不了泄露**（老客户端仍会认旧钥）。

建议终态概念：

```text
CLI 里钉死：Root 公钥（很少动，离线保管更好）
        │
        ▼ 签出
   root.json（谁有权签插件 index、谁有权签升级清单）
        │
        ├─ 业务钥（KMS，可换）──签──► plugin_pkg_index
        └─ 业务钥（KMS）──────签──► 自升级 manifest

可选：短命的 timestamp，防止有人长期扣住「吊销通知」不给你
```

### 3.5 和现有代码的对应关系（落地时看这里）

| 现在 | 建议变成 |
|------|----------|
| `plugin_pkg_index` 里只有 `url` + `checksum` | 整份 index 被签名；checksum **保留** |
| portal 合并写完 index 就上传 | 上传前 **签名**，一并上传 `.sig`（或写进 JSON 的 `signatures`） |
| 插件下载只验包哈希 | **先验 index 签名**，再验包 |
| 自升级直下 | 补上与插件同级的清单签名（至少不要继续裸下） |
| 任意 URL 装包 | 标明「不受信」：强告警 / 默认拒绝 / 企业白名单 |

## 四、怎么分步做（建议节奏）

不必第一天就上完整 TUF。按收益排序：

### 第一步：先把「真实性」做出来（MVP）

- 发布侧对 `plugin_pkg_index`（含 pb 轨）签名并上传。  
- CLI 内置公钥（可先放 `current`，预留 `next`）。  
- index 增加版本号与过期时间。  
- **自升级同步做**，避免短板转移。  
- 验签失败默认中止；不要默认提供「跳过校验」后门。

**这一步已经能挡住：** 只改包、或改了 index 但拿不到私钥的伪造。

**这一步还挡不住得好的：** 若唯一业务钥泄露，且公钥焊死在老 CLI 里——所以第一步结束前就要排第二步。

### 第二步：分层，让换钥 / 吊销可运营

- 客户端只钉 Root；在线学习经 Root 签过的授权变更。  
- 业务钥进 KMS，计划轮换；泄露走「停签 → 换钥 → Root 吊销旧钥 → 重签 index」。  
- 有余力再加短周期 timestamp，压缩「扣住更新」的窗口。

### 第三步：其它增强（按需）

- 任意 URL / 本地包的明确策略。  
- 构建 provenance、可复现构建等（锦上添花，不替代签 index）。

## 五、业务钥泄露时怎么做（心里要有剧本）

1. 立刻停用该钥的签名权限，暂停发布。  
2. 换新业务钥，用 Root 签出「旧钥作废」的授权文件。  
3. 用新钥重签当前 index，版本号 +1。  
4. 发公告；必要时让可能中招的用户从官网带外渠道重装。

Root 本身极少使用、离线分权保管，把「终极灾难」概率压到最低。

---

## 六、建议明确不要做的事

1. 只给 index 旁边再挂一个同 CDN 的 checksum，就当「签过了」。  
2. 公钥和 index 放一起现下，当「信任根」。  
3. 只签单个二进制、不签 index（假条目、回滚、跨平台拼包仍防不住）。  
4. 插件签了、自升级继续裸奔。  
5. 用「双签窗口」当泄露应急方案。  
6. 默认 `--skip-verify`，把 fail-closed 拆掉。

## 七、用一张表收束

| 问题 | 答案 |
|------|------|
| 现在的二进制 checksum 要留吗？ | **要留**，它管完整性。 |
| 再给 index 加一层同站 checksum 够吗？ | **不够**，真实性边界没变。 |
| 一定要公私钥吗？ | **要真实性就要**；没有等价的「普通哈希签名」。 |
| 签什么？ | **签 index / 升级清单**，不是每个包签一份。 |
| 轮转是不是自找麻烦？ | 麻烦来自「钥要可换」；用 **Root 分层** 管理，而不是放弃签名。 |
| 要不要拆两个 CDN 存 checksum？ | **不必**。 |
| 先做什么？ | 签 index + 堵住自升级；再尽快分层，避免业务钥焊死。 |

**一句话记住：**

> checksum 管「对不对得上」；签名管「该不该信这份清单」；版本和过期管「是不是过期货」；Root 分层管「换钥和泄露时还能不能运营」。

把这四层对齐，才是针对当前 aliyun-cli + portal 发布链路的合理方案。

## 八、实现状态（aliyun-cli）

客户端已在分支落地 Phase 1（过渡期兼容未签名索引）：

| 能力 | 位置 |
|------|------|
| Ed25519 分离签名 / 验签 | `cli/trust` |
| `index_version` + `expires_at` 新鲜度 | `cli/trust` + `GetIndex` |
| 可选 `root.json` 委托 | `cli/trust`（有则用，无则回退内置/环境公钥） |
| 插件索引验签 | `cli/plugin/manager.go`（拉 `plugin_pkg_index.json.sig`） |
| 自升级清单 | `cli/upgrade`（优先 `upgrade_manifest.json` + `.sig` + checksum） |
| 任意 URL / 本地包装包 | 明确 warning：不在签名索引信任域内 |
| 本地签名工具 | `tools/artifact-sign` |

环境变量：

- `ALIBABA_CLOUD_CLI_TRUST_ENFORCE=1`：强制要求签名（无 `.sig` 则失败）
- `ALIBABA_CLOUD_CLI_TRUST_PUBKEYS=keyid:base64pub[:role...][;...]`：临时注入公钥（联调）
- `ALIBABA_CLOUD_CLI_TRUST_ALLOW_UNSIGNED`：仅文档保留；**不能**覆盖 Enforce

发布侧仍需：KMS 签 index / upgrade_manifest，并把公钥嵌入 `cli/trust/keys.go`（或走 `root.json`）。
